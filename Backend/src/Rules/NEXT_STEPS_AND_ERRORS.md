# Next Steps & Known Errors

This document outlines the missing pieces required to finish the AI Interview logic, and the known edge-case errors that need to be handled.

## 1. Orchestration Logic (Connecting Socket to AI)
**What needs to change:** 
Currently, the Socket (`interviewSocket.js`) and the AI Evaluation API (`evaluationController.js`) exist independently. We need to bridge them together.
When `transcript:final` is generated by Deepgram, the backend should:
1.  Pass the text to `evaluateAnswer()`.
2.  If the evaluation returns a `followUpQuestion`, the backend should automatically trigger `textToSpeech()` and emit `question:audio` with that follow-up.
3.  If no follow-up is needed, it should pull the *next* generated question from the database and synthesize that instead.

## 2. Managing Conversation State (Context Window)
**What needs to change:**
When asking the AI to evaluate an answer, we currently just pass `{ question, answer }`. As the interview progresses, the LLM needs to know the context of previous questions to maintain a natural conversation flow.
**The Fix:** Update the `evaluationService.js` prompt to accept an array of previous messages (which we can fetch from the `InterviewSession` database) so the AI remembers what was said 2 minutes ago.

## 3. Deepgram Disconnect Edge Cases
**The Error:** `[AudioStream] Deepgram STT closed for SocketID — code 1011` or `code 1005`
**Why it happens:** Deepgram WebSockets automatically close if they don't receive any audio for ~10 seconds, or if the frontend stops sending data abruptly. 
**The Fix:** 
1. The frontend should send a "KeepAlive" signal (empty audio chunks) to prevent timeouts.
2. `audioStreamService.js` needs auto-reconnect logic. If Deepgram closes the connection with code 1000 or 1011 while the interview is still `isActive`, the backend should transparently open a new WebSocket so the user doesn't notice the drop.

## 4. Audio Quality Matching
**The Error:** The TTS output format (`mp3`) and the frontend microphone input format (`webm`) currently work, but the frontend might record at a low sample rate depending on the browser.
**The Fix:** We should explicitly configure the frontend `MediaRecorder` or AudioContext to record at `16000Hz` mono, as this is the optimal rate for Deepgram STT accuracy.
